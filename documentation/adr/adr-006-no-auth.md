# ADR-006: Без аутентификации в V1; данные — локально

Дата: 2026-05-17

Статус: Accepted

## Контекст

Web-версия VMT хостится статически на GitHub Pages, без бэкенда. Пользователь — студент/преподаватель; данные — учебные проекты машин Тьюринга, не содержащие PII.

Рассматривались: отсутствие аутентификации, GitHub OAuth (Device/PKCE) для синхронизации в Gist, Supabase Auth (BaaS).

Требования: NFR-002 (без бэкенда), NFR-003 (без аутентификации), NFR-008 (размер бандла), Safeguards в Canvas (приватность).

## Решение

В V1 **аутентификация не используется**. Приложение полностью клиентское: все данные хранятся локально (`localStorage`, ADR-003), не передаются по сети после загрузки бандла. Перенос между устройствами — через ручной экспорт/импорт `.vmt.json` файла.

Синхронизация через GitHub OAuth и/или Supabase Auth рассматривается отдельно в V1.1 как опциональное расширение, не как часть V1.

## Альтернативы

### Альтернатива 1: GitHub OAuth (Device Flow / PKCE) + Gist storage

Позволяет синхронизировать проекты между устройствами через приватные Gist, не поднимая бэкенд. Минусы:

- требует регистрации OAuth App и хранения `client_id` в публичном бандле;
- PKCE для SPA на GH Pages работает, но редирект-URL должен быть валидным GitHub-доменом;
- усложняет UX (логин, токены, error states);
- увеличивает поверхность атаки (refresh-токены в localStorage).

Не оправдано в V1, где основной use-case — локальная работа.

### Альтернатива 2: Supabase Auth

Внешний BaaS даёт готовую аутентификацию и хранилище, но:

- добавляет внешнюю зависимость (SDK ~50 KB), нарушает NFR-002 (требование «без бэкенда»);
- требует учётной записи Supabase у проекта;
- противоречит Safeguards «не отправлять данные пользователя на сервер».

### Альтернатива 3: Anonymous-режим с device-id

Тривиальный «псевдо-аккаунт» по сгенерированному UUID. Бесполезен без сетевого хранилища; в локальном сценарии уже есть `vmt:projects/<id>` (ADR-003).

## Последствия

Положительные:

- Минимальная сложность: нет логина, токенов, refresh-flow.
- Максимальная приватность: данные не покидают браузер.
- Меньший бандл, нет SDK провайдеров.
- Нет необходимости в CSP-исключениях для домена провайдера.

Отрицательные / компромиссы:

- Нет синхронизации между устройствами «из коробки» (только ручной экспорт).
- Нет облачного бэкапа: чистка кэша браузера = потеря проектов. Митигация — UI-подсказка «Save project as file» + список Recent с предупреждением о локальности.
- Невозможно отслеживать «прогресс по упражнениям» между устройствами; в V1 это устраивает.

## Проверка соблюдения

- В `package.json` нет SDK аутентификации (`@auth0/*`, `@supabase/*`, `firebase`, `keycloak-js`, `oidc-client*`).
- В исходниках нет сетевых вызовов `fetch`/`XMLHttpRequest` к внешним хостам, кроме (опционально) загрузки `exercises.json` с того же origin.
- В CSP не открыты внешние домены (`connect-src 'self'`).
- В UI есть явная кнопка «Export project as file», доступная без необходимости логина.
- В onboarding (или Main-экране) присутствует одноразовое сообщение «Your projects are stored locally in your browser. Export them as files for backup.»
