# ADR-004: Маршрутизация связей — A* + Безье (порт ядра)

Дата: 2026-05-17

Статус: Accepted

## Контекст

В десктопе VMT маршруты переходов строятся `Pathfinder` (A* по сетке со штрафом за поворот, упрощение, ортогонализация, выравнивание терминалов; см. [`../rendering.md`](../rendering.md)) и отображаются кривыми Безье через `DiagramBezier` (Catmull–Rom → кубический Безье, горизонтальные касательные у портов). Это поведение даёт читаемые диаграммы:

- мало изломов;
- параллельные связи разнесены;
- стрелка входит горизонтально в центр узла;
- клик попадает по криволинейной связи (через `QPainterPathStroker`).

Для веб-версии надо повторить поведение «1-в-1», иначе:

- ломаются визуальные тесты и снапшоты;
- ухудшается UX (зигзаги, наложения);
- расходится PNG-экспорт.

Рассматривались: порт алгоритмов на TS, готовые библиотеки `dagre`/`elkjs`, авто-сплайны/d3-shape.

Требования: FR-007, FR-008, NFR-006.

## Решение

Портируем алгоритмы из C++ в чистый TypeScript в модуле `@core/routing/`:

- `pathfinder.ts` — A* (8-связная сетка, штраф за поворот), `simplifyPath`, `optimizeOrthogonalPath`, `enforceTerminalDirections`, учёт уже построенных путей через «коридор» (`pathCorridor`).
- `bezier.ts` — `buildConnectorPath` (Catmull–Rom → cubic), `flattenPath`, `isPointNearStroke`, `snapPortHeights`.

Тесты — Vitest, в качестве референса — те же сценарии, что и `tests/pathfinder/test_pathfinder.cpp` (12 кейсов, доказавшие себя в десктопе).

Маршрутизатор работает в основном потоке. Если в нагрузочных замерах FPS падает ниже 30 на 200 узлах / 400 связях — выносим в Web Worker (V1.1, отдельное решение).

## Альтернативы

### Альтернатива 1: dagre / elkjs

Готовые auto-layout библиотеки делают раскладку графа целиком, а не маршрутизацию между фиксированными точками. Это меняет UX: пользователь не сможет управлять положением узлов руками. Несовместимо с FR-003 (drag-n-drop) и FR-019 (зум как у десктопа).

### Альтернатива 2: Авто-сплайны d3-shape / curve-fitting

Без сетки и обхода препятствий получаем красивые, но проходящие сквозь узлы линии. Это противоречит десктопной модели и портит читаемость.

### Альтернатива 3: Свой алгоритм маршрутизации с нуля

Долго, дорого, нет гарантий, что повторим качество текущей реализации. Существующий код уже покрыт тестами — порт даёт известное поведение «бесплатно».

## Последствия

Положительные:

- Поведение и качество маршрутов идентичны десктопу.
- Готовые тестовые сценарии переиспользуются.
- Алгоритмы независимы от UI и могут жить в `@core` (тестируются в Node без DOM).

Отрицательные / компромиссы:

- A\* в JS на порядок медленнее C++ → для крупных диаграмм может понадобиться Web Worker (план V1.1).
- Логика штрафа за повороты и «коридора» путей чувствительна к параметрам; их значения переносим как константы и фиксируем в тестах.
- Шрифт меток (`textWidth`) при экспорте PNG надо измерять через тот же Canvas-контекст, иначе анкер метки сместится.

## Проверка соблюдения

- Каталог `src/core/routing/` существует и экспортируется через `@core/routing`.
- В тестах присутствуют сценарии-аналоги `tests/pathfinder/test_pathfinder.cpp` (12 кейсов).
- В UI нет прямых вызовов алгоритма раскладки сторонних библиотек (нет импорта `dagre`, `elkjs`, `d3-shape`).
- Профайлинг FPS (Playwright trace) на бенчмарке 200×400 удовлетворяет NFR-006.
- Бенчмарк pathfinder в Vitest (`bench`) фиксирует регрессию > 30% по времени.
