# Пример REASONS Canvas для первой версии мессенджера

## Метаданные

- Название изменения: Первая версия приложения "..."
- Связанные требования: FR-001..., NFR-001...
- Связанные ADR: ...

## R — Requirements

- Пользователь входит через Keycloak, видит свои чаты, читает историю и отправляет сообщение.
- В первую версию входят только личные чаты, REST API и хранение сообщений в PostgreSQL.
...

## E — Entities

- `User` — локальное представление пользователя из Keycloak.
- `Chat` — личный чат между пользователями.
...

## A — Approach

- Начать с REST API, потому что его проще реализовать, тестировать и объяснить в рамках мастер-класса.
- Использовать Keycloak как внешний identity provider, а backend сделать resource server, который проверяет JWT.
...

## S — Structure

- Frontend: React-приложение, API-клиент, компоненты чатов и сообщений.
- Backend: FastAPI, маршруты `/health`, `/chats`, `/chats/{chat_id}/messages`, JWT dependency, модели данных.
...

## O — Operations

1. Создать или обновить требования и ADR.
2. Создать backend healthcheck и тест.
3. Добавить модели данных и тесты доступа к чатам.
...

## N — Norms

- Не добавлять новые зависимости без причины.
- Держать публичный API простым и отраженным в OpenAPI.
- Писать проверяемые тесты для ключевых сценариев.
- Обновлять README, если меняется локальный запуск.
- Сохранять prompt-артефакты в `documentation/prompts/`.

## S — Safeguards

- Не хранить пароли пользователей в backend.
- Не коммитить реальные секреты.
- Не допускать чтение или запись чужих чатов.
- Если меняется поведение API, сначала обновить требования и Canvas.
- Если выполняется рефакторинг без изменения поведения, синхронизировать Canvas после изменения кода.
